# Agile Software Development and SOLID Principles Study Guide

This study guide provides a comprehensive overview of agile software development, its history, values, and methodologies, as well as the foundational SOLID principles of object-oriented design. It is synthesized from provided documentation to assist in mastering the core tenets of modern software engineering.

---

## I. Key Concepts and Overviews

### The Agile Manifesto
Agile software development is an umbrella term for development approaches based on the *Manifesto for Agile Software Development*, authored in 2001 by the 17-member Agile Alliance. The mindset prioritizes four core values:
1.  **Individuals and interactions** over processes and tools.
2.  **Working software** over comprehensive documentation.
3.  **Customer collaboration** over contract negotiation.
4.  **Responding to change** over following a plan.

### Core Principles of Agility
Agile development is governed by 12 foundational principles, which emphasize customer satisfaction through early delivery, welcoming changing requirements, frequent releases (weeks rather than months), and building projects around motivated, trusted individuals. Success is primarily measured by the delivery of working software.

### Methodology and Philosophy
*   **Iterative and Incremental:** Development is broken into short "timeboxes" called iterations or sprints, typically lasting one to four weeks. Each iteration involves a cross-functional team performing planning, analysis, design, coding, and testing.
*   **Adaptive vs. Predictive:** Agile methods are "adaptive," focusing on responding to changing realities and "rolling wave" scheduling. This contrasts with "predictive" (Waterfall) methods, which rely on detailed, early-phase analysis and rigid plans.
*   **Communication:** Face-to-face conversation is considered the most efficient communication method. Teams often use "information radiators" (large physical displays) to show real-time progress.
*   **Quality Focus:** Practices such as continuous integration (CI), test-driven development (TDD), and pair programming are used to build quality into the product from the start.

### SOLID Design Principles
SOLID is an acronym representing five essential principles for object-oriented programming design:
*   **S:** Single responsibility principle
*   **O:** Open–closed principle
*   **L:** Liskov substitution principle
*   **I:** Interface segregation principle
*   **D:** Dependency inversion principle

## IV. Glossary of Important Terms

| Term | Definition |
| :--- | :--- |
| **Acceptance Test-Driven Development (ATDD)** | A methodology based on communication between business customers, developers, and testers to understand needs before implementation. |
| **Agile Smell (Anti-pattern)** | Common pitfalls or difficulties organizations face when transitioning to or implementing agile methods. |
| **Backlog** | A prioritized list of functionality (Product Backlog) or tasks for a specific iteration (Sprint Backlog). |
| **Continuous Integration (CI)** | The practice of merging code changes into a shared codebase frequently (often daily) and using automated builds and tests to ensure stability. |
| **Cross-functional Team** | A multidisciplinary group with all the functional expertise (finance, marketing, coding, testing, etc.) necessary to reach a common goal. |
| **Daily Stand-up** | A brief, daily meeting (usually 15 minutes) where team members review progress and identify impediments while standing to ensure brevity. |
| **Information Radiator** | A prominent physical display (like a board with sticky notes) that provides an up-to-date summary of development status to passers-by. |
| **Iteration (Sprint)** | A short, fixed timebox (typically 1–4 weeks) during which a cross-functional team completes a specific set of work. |
| **Method Tailoring** | The process of adapting a development approach to a specific project situation by changing or combining method fragments. |
| **Pair Programming** | An agile technique where two developers work together at one workstation to improve code quality. |
| **Refactoring** | The process of modifying the internal structure of code to improve its design without changing its external behavior. |
| **Technical Debt** | The implied cost of additional rework created by choosing an easy or quick solution now instead of a better approach that would take longer. |
| **Timeboxing** | The act of allocating a fixed, maximum unit of time to an activity. |
| **Velocity** | A metric used in some agile studies to measure a team's rate of progress or agility. |
| **Waterfall Model** | A sequential development process where work moves through distinct phases (requirements, design, build, test) in order. |
